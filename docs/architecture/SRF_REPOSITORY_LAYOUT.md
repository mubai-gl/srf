# SRF 仓库目录规划

状态：初始化结构建议，供 SRF 研发中心在获得授权后采用；运行框架内部的精确模块与文件协议留待详细设计确认。

## 1. 目标结构

```text
SRF/
├── README.md                     # 人类入口、使用与导航
├── AGENTS.md                     # AI 研发入口，仅索引及必要约束
├── .gitignore
├── docs/                         # SRF 自身研发资料，不进入运行包
│   ├── project/                  # 章程、初始/正式需求、路线图
│   ├── architecture/             # 顶层设计、目录规划、详细设计
│   ├── research/                 # 理论研究、来源与取舍
│   └── decisions/                # 重要架构决策与理由（ADR）
├── management/                   # SRF 自身研发状态
│   └── PROJECT_STATE.md          # 唯一当前状态入口
├── instructions/                 # SRF 研发中心的 Project 指令
├── framework/                    # 正式框架运行源文件（后续建设）
│   ├── core/                     # 核心治理、权限、规则契约
│   ├── orchestration/            # 意图、编排、上下文、执行与恢复
│   ├── capabilities/             # 产品、需求、架构、开发、测试等
│   ├── governance/               # 工程质量、风险、安全、变更
│   ├── knowledge/                # 经筛选的运行知识
│   ├── adapters/                 # GitHub、运行平台、外部工具适配
│   ├── extensions/               # 可选领域扩展
│   ├── templates/                # 运行时使用的模板
│   ├── evolution/                # 软件项目侧反馈、升级与迁移规则
│   ├── entrypoints/              # 软件 Project 启动入口与指令
│   └── manifest.yaml             # 模块索引、依赖与发布边界（格式待定）
├── tests/                        # 框架测试（非业务软件测试）
│   ├── behavior/                 # AI 行为、授权与回归用例
│   ├── structural/               # 结构、引用、契约与发布清单检查
│   ├── migration/                # 安装、升级与回滚测试
│   └── fixtures/                 # 跨领域测试素材
├── scripts/                      # 构建发布包、校验、迁移等辅助脚本
└── .github/                      # Actions、Issue/PR 模板（按需）
```

此树表示目标职责，不表示文件或运行模块已经实现。Git 不跟踪空目录；初始化时仅建立真实文件所在目录，不批量创建占位文件。根目录保持简洁，未来仅在实际需要时加入 LICENSE、CHANGELOG.md 等入口文件。

## 2. 目录边界与唯一来源

- `docs/` 保存研发中的设计、研究与决策；`framework/` 保存实际供软件 Project 加载的有效运行规范。研究笔记不能自动成为强制规则。正式规范只在其所属模块维护，设计文档引用规则 ID 或路径，不再复制全文。设计理由保存在必要的决策记录中。
- `instructions/` 是研发 SRF 的指令；`framework/entrypoints/` 是使用 SRF 开发软件的指令。不得混用。
- 八大逻辑体系不强制一一对应八个物理目录。核心治理与项目研发治理、编排与专业能力分别明确责任；知识与状态的运行规则按职责归属，实际业务状态由软件项目保存。模块拆分与合并按真实需要进行。
- `management/PROJECT_STATE.md` 仅保存 SRF 自身当前阶段、阻塞、当前任务链接、下一步等恢复信息；详细任务、缺陷和反馈优先使用 GitHub Issues，状态来源不重复。无 Issues 能力时，才设计最小仓库文件替代方案。
- `tests/` 独立于运行文件；测试与历史缺陷、规则 ID、必要的决策关联。实验原始素材与发布运行知识隔离。
- `framework/manifest.yaml` 是规划中的运行索引和发布清单入口；记录稳定模块 ID、路径、依赖及必要兼容信息，具体格式在文件与协议设计阶段确认。不与 README 或 AGENTS 重复维护完整模块清单。

## 3. 最小充分文件策略

文件是为职责、事实和实际使用服务的，不以仓库存储容量、文件数或文档数量衡量研发成果。新增文件前先检索现有权威文件，优先原位更新或合并；仅当存在独立职责、独立生命周期、明确的复用/加载边界、权限边界或必要的测试/自动化入口时才拆分。新增目录同样须有真实职责与内容。禁止为了格式整齐、阶段仪式、重复摘要、历史副本或一条规则一份文件而增加文件。

不设机械的文件数或行数上限：过度拆分与巨型混杂文件都应避免。按变更风险审视新增必要性、关联入口和维护成本；常规合理新增无需逐文件征求用户批准，重大结构变更依照既有授权规则。发现重复、无效或失去职责的文件时，先检查引用、依赖与兼容性，再在授权范围内合并或删除。优先复用 GitHub 原生能力。文件策略的权威细则在本节，其他文档仅保留必要约束或引用。

## 4. 迭代与发布规则

普通文件使用稳定名称和路径，不加版本号、不建历史副本。Git 管理文件历史，Git Tag/Release 管理框架整体发布。移动、合并或删除模块时，同步检查索引、引用、依赖、测试和迁移影响；不得为兼容盲目保留旧文件。

运行包通过明确的发布清单从 `framework/` 及必要的安装/迁移工具生成；发布时校验依赖闭包、引用和必需入口，排除研发资料、管理状态、测试素材和私密信息。构建产物不重复提交主分支；正式归档使用 GitHub Releases。软件仓库部署到 `.srf/`，项目配置与业务状态继续独立于 `.srf/`。

SRF 主仓库在首发前只使用 `main`；分支、PR 和实验分支按顶层设计 9.2 延后启用。首发前不为目录改造额外创建分支。

## 5. 本次启动包的真实文件

- 根目录：`README.md`、`AGENTS.md`、`.gitignore`
- `docs/project/`：项目章程、初始需求、研发路线图
- `docs/architecture/`：顶层设计、本文
- `instructions/`：SRF 研发中心启动指令
- `management/`：初始状态记录（尚未执行 GitHub 初始化）

后续由 SRF Project 根据研发进度逐步建立运行文件、研究、决策、测试和脚本。不得把上述目标树或本启动包当作已实现的框架。
