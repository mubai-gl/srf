## 2. 目录边界与唯一来源

- `docs/` 保存研发中的设计、研究与决策；`framework/` 保存实际供软件 Project 加载的有效运行规范。研究笔记不能自动成为强制规则。正式规范只在其所属模块维护，设计文档引用规则 ID 或路径，不再复制全文。设计理由保存在必要的决策记录中。
- `instructions/` 是研发 SRF 的指令；`framework/entrypoints/` 是使用 SRF 开发软件的指令。不得混用。
- 八大逻辑体系不强制一一对应八个物理目录。核心治理与项目研发治理、编排与专业能力分别明确责任；知识与状态的运行规则按职责归属，实际业务状态由软件项目保存。模块拆分与合并按真实需要进行。
- `management/PROJECT_STATE.md` 仅保存 SRF 自身当前阶段、阻塞、当前任务链接、下一步等恢复信息；详细任务、缺陷和反馈优先使用 GitHub Issues，状态来源不重复。无 Issues 能力时，才设计最小仓库文件替代方案。
- `tests/` 独立于运行文件；测试与历史缺陷、规则 ID、必要的决策关联。实验原始素材与发布运行知识隔离。
- `framework/manifest.json` 是已批准的运行索引和发布清单入口；字段及严格解析见协议设计第1节，产物完整性和兼容细节见已批准协议第9节。不与 README 或 AGENTS 重复维护完整模块清单。

## 3. 最小充分文件策略

文件是为职责、事实和实际使用服务的，不以仓库存储容量、文件数或文档数量衡量研发成果。新增文件前先检索现有权威文件，优先原位更新或合并；仅当存在独立职责、独立生命周期、明确的复用/加载边界、权限边界或必要的测试/自动化入口时才拆分。新增目录同样须有真实职责与内容。禁止为了格式整齐、阶段仪式、重复摘要、历史副本或一条规则一份文件而增加文件。

不设机械的文件数或行数上限：过度拆分与巨型混杂文件都应避免。按变更风险审视新增必要性、关联入口和维护成本；常规合理新增无需逐文件征求用户批准，重大结构变更依照既有授权规则。发现重复、无效或失去职责的文件时，先检查引用、依赖与兼容性，再在授权范围内合并或删除。优先复用 GitHub 原生能力。文件策略的权威细则在本节，其他文档仅保留必要约束或引用。

## 4. 迭代与发布规则

普通文件使用稳定名称和路径，不加版本号、不建历史副本。Git 管理文件历史，Git Tag/Release 管理框架整体发布。移动、合并或删除模块时，同步检查索引、引用、依赖、测试和迁移影响；不得为兼容盲目保留旧文件。

运行包通过明确的发布清单从 `framework/` 及必要的安装/迁移工具生成；发布时校验依赖闭包、引用和必需入口，排除研发资料、管理状态、测试素材和私密信息。构建产物不重复提交主分支；正式归档使用 GitHub Releases。软件仓库部署到 `.srf/`，项目配置与业务状态继续独立于 `.srf/`。

SRF 主仓库在首发前只使用 `main`；分支、PR 和实验分支按顶层设计 9.2 延后启用。首发前不为目录改造额外创建分支。

## 7. 物理架构与候选文件职责（F01–F03）

### 7.1 三类权属及部署映射

- SRF研发仓库：根README/AGENTS、docs/、management/、instructions/仅为研发导航、研究、设计、当前状态和研发中心启动指令；不随软件运行包分发。tests/、scripts/及.github/按真实任务建设；测试素材、开发工具与实验不默认为运行依赖。
- 运行源：framework/为实际可发布规范及必要资源的唯一维护来源。发布清单从指定源提交选择经审查的文件；目录不是授权或发布白名单，不能默认整树复制。包内相对路径保持稳定，源framework/<相对路径>映射至软件项目.srf/<相对路径>（没有额外framework嵌套）。项目可通过独立授权环境安装指定版本，不自动取研发仓库main。
- 软件项目自有：.srf-project/为独立项目配置、反馈、迁移资料的权属边界；业务源码、测试、文档、数据和已有管理状态保留原位置。普通升级仅操作核实归属的.srf/受管文件，必要项目迁移单独明确授权。软件项目不读取研发中心docs/或management/才能启动，不在业务代码中引入SRF运行依赖。退出保护项目资料，真实前后构建及必要运行按REQ-052验证。

三类文件不因位于同一仓库而拥有同一权威。有效Project根绑定仍由用户确认的Project配置产生，不从包、目录名、配置副本或普通文件反推授权。状态与配置可含权威引用，不保存密钥及无必要隐私。目录职责不是底层权限隔离，实际访问和写入仍由J01/J04/J14–J16/J35–J37控制。

### 7.4 稳定路径、索引与命名

既有研发文件名保持原样，不为了统一风格重命名。新运行正文使用短英文小写kebab-case及.md（入口文件沿用清晰的PROJECT_INSTRUCTIONS.md，manifest沿原规划）。正文优先自然语言Markdown，可解析的少量元数据、配置和必要机读证据按FP-02–06选型；不要求每次用户对话或专业输出序列化。路径相对于明确根，区分大小写，拒绝绝对路径、越界、重复/冲突和不明重定向；实际适配需核实平台路径语义，不能仅靠字符串检查保障解包安全。普通文件名无版本后缀，稳定逻辑ID不随物理移动机械改变；公开路径/契约的变更须评估兼容及迁移（REQ-041/046）。不把内部所有路径都公开为永久接口。
