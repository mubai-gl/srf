## 3. 第一轮融合与裁剪分析

| 重叠/冲突 | 候选处理 | 适用边界与失败情形 |
|---|---|---|
| SWEBOK 知识覆盖 vs ISO 生命周期 vs PMBOK/IIBA | 知识覆盖、活动组织、价值/治理及需求分析分别作为视角；按 SRF 八体系及需求归属整合，不建立四套重复规则。 | 出版摘要不足以确定具体强制活动；不宣称标准合规，不以 18 知识域要求 18 个物理模块。 |
| 计划驱动 vs Scrum/流动实践 | 以风险、复杂度、自主授权与成果依赖裁剪；用增量、反馈、适度计划服务任务。 | 用户不必选流程，不为固定 Sprint、会议或角色造工作；若软件项目明确采用 Scrum，则按其完整定义及项目约束实施。 |
| 需求追踪 vs 用户简单性 | 核心需求、重要决定、实现和验证保持稳定关联；普通小改仅记录必要事实。 | 追踪不能代替真实验收，不重复用户已知输入；原话、AI 建议、批准需求保持不同语义。 |
| Clean Architecture 与文档式运行内核 | 将工具独立、稳定契约、唯一规则来源、依赖可定位作为设计候选；专业知识按需加载。 | 不照搬类/接口/四层架构；低耦合需通过替换、引用、回归实验验证，而非凭目录判断。 |
| TDD/CI 与概率性 AI | 对结构、引用、脚本等确定性对象优先自动测试；对 AI 行为使用重复场景、真实工具证据及人工校准。 | AI 自评不等于独立测试，生成测试不等于执行；无法执行时明确降级，不把一次成功视为永远可靠。 |
| Agent 自主性与安全 | 优先简单路由、可验证任务和按需工具；权限由显式授权与外部可用保障约束。 | 数据注入、未知响应、工具调用超时均可能失败；不因模型更强或角色切换扩大权限；不把文本约束视为安全隔离。 |
| 上下文完整与经济性 | 小型可信入口 + 任务/专业/扩展按需获取；事实来自指定版本仓库。 | 漏读规则、过期索引、超长文件、工具不可读是失败场景；须能停止、降级与恢复；不得以对话摘要替代权威事实。 |
| 评估可追溯与隐私 | 记录必要版本、任务、实际结果与失败，敏感字段最小化；对照研究保留偏差及局限。 | 不机械记录所有原始输入或日志；不因平均分改善豁免安全失败；无法测量成本记录未知。 |
| 版本兼容与维护负担 | 采用整体发布及必要公共契约标识，普通文件原位更新；项目配置与锁定核心隔离。 | 必须定义何为公共契约并验证升级/回滚；现有需求已批准版本原则，具体协议待设计。 |

### 6.2 生命周期与流程裁剪候选机制（R01）

以 012、013、016、025 为约束，候选设计：活动可以组合、重复或并行；流程仅描述当前任务所需的活动组合与依赖，治理统一生效。S01 为知识/需求依据，S06 为管理裁剪参考，S07/S08 为反馈与流动参考，S21 为高风险裁剪的实践案例。S02 仅作版本/生命周期范围参考，不作标准合规声明。

| 情境（假设素材，非实际测试） | 候选最小活动组合 | 必须保留的约束 |
|---|---|---|
| 已授权、低风险局部修订 | 定位、修改、差异/适当验证、必要状态更新 | 授权、真实证据、无无关修改；不强制新 SRS 或独立计划 |
| 需求明确的小功能 | 确认目标及验收、局部设计、实现、验证、交接 | 涉及公共接口或新范围时升级决策级别 |
| 意图模糊的探索 | 需求澄清、选项比较、隔离原型、反馈 | 原型不自动进入正式实现；讨论不授予写入权限 |
| 低复杂度但高风险操作 | 影响与风险分析、明确批准、恢复方案、验证 | 不因工作量少而降低授权、备份或验收 |

这不是固定六种流程或新的等级。复杂度、风险、自主程度分别判断；若缺少关键授权、事实或前置条件，停止受影响的动作；能安全继续的独立工作仍可在原授权内开展。过程裁剪仅移除不适用活动和重复记录，不能删去适用的强制保障。重要裁剪记录理由与影响，不为每次普通小改新建裁剪表。相比固定流程，预期降低冗余；仍有遗漏必要活动风险，需对照验证。

### 6.3 需求工程候选机制（R02）

S01 第1章 4.5、5、6.1–6.2 相关段落支持以可理解、可检查的需求及变更维护为目标，评审与原型可用于验证需求。S05 4.4 与生命周期任务入口为需求层次、追踪及变更提供参考。基于 001、007–010、017、023、028、032 的 SRF 原创候选处理如下：

- 接收：保留必要的原始意图来源（隐私最小化），区分产品目标、利益相关者需要、解决方案能力/质量、过渡约束及纯实现建议。无需每项都生成四层文档。
- 分析：结合项目事实明确行为、适用范围、排除事项、重要限制和验收场景；区分未知假设、冲突、可接受默认值、待确认决策。
- 确认：需求是否反映真实意图（确认/validation）与规格是否清晰、一致、可检查（规格质量/verification）分别检查；用户确认不能被静态检查替代。重大需求与授权分别记录，不能以认可需求推断仓库写入权限。
- 维护：已批准需求使用稳定 ID、权威来源、批准状态、优先级、必要验收与关联；只有重要关系才记录详细双向定位。当前规格原位更新、Git 保存差异；不再额外维护重复矩阵或独立版本副本。具体字段与状态转换待 PH-06/07。
- 变更：识别影响（价值、范围、依赖、接口、设计、验证、安全、成本、兼容），区分建议、批准、实施、验证；拒绝或暂缓也保留必要理由。不因紧急而越权。
- 验收：把已批准需求与实际实现、验证证据和最终使用者验收关联；条件未满足时不标为完成。需求批准和软件验收是不同事件。

示例：用户说“这个模块应该更简单”，属于意图/反馈，不能直接作为删除授权。AI 可分析冗余和维护代价、提出候选方案；只有任务范围与权限明确后才执行，实际差异及回归结果独立记录。此示例为纸面场景，不是运行测试。

### 7.2 SOLID 的裁剪应用（R05）

| 原则 | SRF 候选行为 | 禁止机械类比与验证方向 |
|---|---|---|
| SRP 单一职责 | 依据责任及变化原因划分，规则唯一权威来源，设计理由与规范各有职责 | 不等于一规则一文件；用规则变更检验是否需要修改无关模块 |
| OCP 开闭 | 专业能力与工具适配优先扩展既有契约；核心可按批准的影响分析与回归受控重构 | 不冻结核心；扩展点必须有真实使用及维护收益 |
| LSP 替换 | 替换实现时维持声明的输入、输出、安全、失败及证据语义 | 工具缺少能力时明确不兼容或降级，不假装等价；用契约/行为回归验证 |
| ISP 接口隔离 | 最小必要输入输出及按需加载，模块不依赖无关知识 | 不为每一项行为生成接口文件；关注总加载成本和缺失约束 |
| DIP 依赖倒置 | 通用治理和研发能力定义工具无关需求与契约，由适配映射具体能力 | 无需对象继承、IoC 容器；工具实际限制及平台安全仍不可绕过 |

关联 002,004,006,019,023,034,044,046,048,049。候选结论：按需适用的原则比强制面向对象结构更符合首版文档式运行环境。公共契约应由实际使用、稳定语义与兼容需求驱动；不要预先抽象尚不存在的变化。

### 7.3 模块、契约及依赖语义（R06）

候选区分四种关系：治理约束（不可由下层覆盖）、必要加载/执行前置（应可检查依赖闭包及实际循环）、语义追踪（可以双向关联，不等于加载依赖）、运行调用/结果回流（可双向交互，不改变规则优先级）。同一对象在不同视图中的关联不能混为单一依赖图。必要前置循环应在设计阶段消除或明确可终止机制；仅有双向需求引用不能判定模块循环。

模块应围绕已批准 004、044、048 的职责与契约设计，至少能定位职责、适用/非适用、输入输出、必要依赖、权限、失败/降级、完成证据、关联测试及稳定 ID；具体字段和存储格式留 PH-06/07。内部策略与知识可局部演进；核心治理、公共契约、入口及迁移涉及高风险变更须按既有授权处理。一个职责允许多个实际加载单元，一个文件也可承载若干紧密相关职责。先判断变更耦合及真实使用边界，再决定拆分合并。

方向：稳定入口加载通用治理，任务编排按需定位专业能力；专业能力提出工具无关操作需求，适配负责平台映射及能力不足反馈。工具返回的数据不能产生新授权。没有强制独立程序层级、固定文件数量或额外框架引擎。架构的规范依赖与实际调用方向可不同。静态结构检查能发现无效引用、非法依赖、重复 ID；自然语言语义冲突和模型是否实际遵循仍需行为测试，不能用图结构代替。

### 7.4 GoF 与 DDD 的候选取舍（R07、R08）

GoF 用作设计问题工具箱，不将23种模式列为必需实现。适配器思想适用于屏蔽 GitHub/运行平台差异；策略思想适用于按任务选择研发活动；外观思想适用于统一自然语言入口。仅有真正复用问题才进一步采用组合、观察者或命令等设计；不能因名称相似就宣称已实现 GoF 模式。首版不预建工厂、事件总线、插件注册平台或复杂对象体系。关联 001,002,006,012,016,018,034,048。

DDD 战略设计思想可帮助区分需求批准、任务授权、实际执行、验证、发布等术语的适用范围；例如“完成”必须说明是需求确认、实现完成、测试通过还是业务验收；“项目”应区分 SRF 研发中心与软件项目；框架规则、软件事实、工具数据的权限来源不可混同。内部概念应一致、跨边界显式翻译，用户仍使用自然语言，AI 负责解释。软件业务领域自身可能需要 DDD 战术设计，SRF 不默认强制实体/聚合/仓储/微服务/CQRS，不为术语划分创建独立运行模块。关联 007,008,009,028,029,033,037,044。术语、状态与契约具体语义后续设计，非本轮新增强制规则。

### 8.1 证据范围

### 8.2 风险驱动的最小充分测试（R10）

依据 S14 的测试设计和风险思想，保持任务裁剪与关键质量门槛分离。测试从需求和风险开始，先明确预期、前置、可观察证据与影响范围；再选择合适技术。缺陷复现与修复确认针对原问题，回归验证针对变更的其他影响，两者不能互代。测试全通过只能说明给定条件下所测范围，不能证明无缺陷。结合 020,025,029,032,040,047,049：

| 适用技术 | SRF 候选验证对象 | 证据/注意 |
|---|---|---|
| 等价类与边界 | 合法/非法绑定、有效/失效授权、输入长度或配置阈值、兼容版本 | 有序阈值才使用数值边界；自然语言语义不能仅靠字符串长度 |
| 决策表 | 模式、授权、目标身份、风险、工具能力的允许/拒绝/降级组合 | 覆盖可行关键组合；不真实访问白名单外仓库 |
| 状态转换 | 候选/批准/执行/验证/验收、暂停与恢复 | 状态不可因文档声称成功而跃迁；非法转换应阻止 |
| 静态检查 | ID、引用、配置、依赖、清单、语义审查 | 结构自动检查与 AI 语义审查分开；静态不能代替运行 |
| 实际运行与回归 | 受控样本构建、测试、故障恢复、升级/退出、已知缺陷 | 绑定相同版本与环境，实际输出保留；修复确认与影响回归均需适用证据 |
| 探索性及行为评价 | 歧义请求、注入、工具错误、长上下文、重复运行 | 预设不可接受行为，保留反例及评价限制；WP-05/06 深化 |

TDD（S11）作为可执行确定性对象的推荐候选：先定义测试，确认失败原因与预期缺失一致，最小实现，再重构及回归。对规则、文档和概率性行为可先制定验收/反例，不把一次自然语言响应通过称为 TDD 或单元测试。未有执行能力时输出待验证的用例及交接，不造测试输出。不得为了满足测试而弱化已批准需求或篡改预期。

### 8.3 版本绑定的证据和质量门槛（R11）

沿用顶层设计 8.2 与 REQ-029 E0–E5，以下只解释使用，不重新定义类别：E0 推测、E1 静态检查、E2 构建、E3 自动化测试、E4 实际运行、E5 业务验收。不同证据不是线性替代关系；自动化结构校验可同时具有 E1 内容与 E3 执行证据，须说明实际验证对象，不能以其证明业务功能。

候选最小记录：验证目标/需求、被测版本（commit 或 Release 与必要产物标识）、环境及工具、范围/前置、实际执行或来源引用、预期、实际结果、结论、限制。适度复用 CI、commit、测试报告、Issue 或当前状态，不维护重复证据库；原始日志最小化和脱敏，不能保存密钥。具体字段和格式待 PH-06/07。

| 事实 | 判定方式 |
|---|---|
| 已生成/写入 | 文件/提交实际回读与差异；不自动表示测试通过 |
| 已构建 | 真实构建运行及版本匹配；不自动表示功能正确 |
| 已测试 | 明确执行范围、结果、失败、跳过/未运行；不能以工具可用或计划代替 |
| 验收通过 | 对必要条件逐项核实与适当人类验收；不得冒充独立审查 |
| 失败/未知/阻塞 | 分开标记；不得以缺证据当成功、失败或不存在；核实或交接 |

D01/D02/D06 的发布门槛已经批准，此研究不另创门槛或豁免。建议每次适用检查在变更前定义完成条件；失败或缺少必需证据时停在相应阶段。不能以整体平均分抵消关键安全失败。刻意注入错误并正确拒绝/恢复是测试成功，真实关键缺陷须诊断、修复与复验，保留历史失败。独立人工/工具评价按风险引入；AI 模拟多角色不能称独立审查。样本量与统计阈值 WP-06/PH-10 确定。

### 8.4 安全软件工程与领域验证（R12）

NIST S15 概览为准备、保护、研发和漏洞响应提供研究视角；S28 仅用于 Web 安全控制研究方向，不假设所有领域适用相同检查。面向 SRF 的候选归并：执行前核实身份、授权、能力、敏感数据和依赖/许可风险；保护核心规范、项目配置及版本来源；开发期间按技术栈选择静态/动态检查、安全设计及依赖核验；发现缺陷后限制影响、记录复现和修复依据、回归防复发。AI 特有注入与工具风险由 WP-05 深化，避免维护两套安全规则。关联 023,024,025,027,034,037,039,040,047。用合成素材验证拒绝、最小披露、配置保护和漏洞回归；不实际越界或对第三方目标测试。工具无法扫描时如实标未验证。安全风险可前置裁剪，但适用强制保障不得省略；不宣称符合 SSDF 或 ASVS，完整控制需合法获取及按具体项目研究。

### 8.5 Git 受控事务与异常恢复（R13）

原生 Git S27 的条件引用更新、普通推送防止非快进及 revert 新建补偿提交，为既有顶层设计 9.1 与 014,034,035,043 提供实践依据。不能据本地 Git 文档推断 GitHub API 或连接器所有接口具有同样的原子/并发语义。候选操作链：核对仓库、分支、授权、基础 HEAD、当前文件 SHA 和引用；准备完整逻辑变更及预期差异；多文件依赖变更优先已验证的单次逻辑提交；最终移动授权分支引用时要求预期 HEAD 及非强制更新；回读实际引用、提交及文件内容，检查无关路径未变化，必要时核对 CI。Git 对象创建与分支可见提交是不同事实；一次引用更新不代表外部副作用、CI、状态或发布原子完成。

| 异常 | 候选处理及后续验证 |
|---|---|
| 基线/Blob 变化 | 停止受影响操作，重新读取差异与授权，协调后再执行；不盲目覆盖 |
| 写入返回超时或未知 | 查询当前 HEAD、预期提交/文件及实际差异；已落实则不重复提交，未落实才按新确认状态处置，仍未知则停止 |
| 串行多文件部分写入 | 识别已完成、未完成及不一致范围，停止相关工作；协调补齐或经授权补偿，保留实际证据 |
| 已知错误提交 | 核查后续提交、配置/数据影响及回滚授权；优先补偿提交或 revert，而非改写历史；Git 恢复不等于业务数据自动恢复 |
| 能力不足 | 降级为经核实的串行写入或交接补丁，说明风险与限制；无法安全执行则不写入 |

PH-02 已实测陈旧 Blob SHA 冲突、普通批量操作及清理；本轮既有 main 提交继续使用预期 HEAD 检查和非强制更新，但未专项注入分支头并发冲突、部分写入或超时，故不称这些验证通过。后续仅在授权受控素材、本地环境或绑定仓库的明确范围内验证；不得新建分支/PR 或访问其他仓库。现有 main 未启用保护，不能宣称系统强制。适配协议详细化留 PH-06/07。

### 8.6 持续集成、交付与发布（R14）

S10/S30 的候选应用：以版本为起点建立适当的快速检查、构建/实际测试、深度及人工验证、可安装产物与发布审批的依赖关系；快速反馈和全面验证有成本取舍，不能以速度豁免必须的保障。首版不预设复杂 CI 平台，按可用环境优先确定性检查并保留实际结果；无 CI 时手工或可用工具执行及交接，不能称已自动化。持续集成不等于每次提交直接部署，自动构建通过不等于发布批准。SRF 自身只在 main 研发直至首发，项目级分支策略不强制给业务项目。

候选交付路径：由确定版本构建运行包 → 校验必要入口、依赖闭包、排除研发资料/私密信息、许可与产物标识 → 实际验证指定版本安装、升级、迁移、回滚和退出（保护配置及业务）→ 核实已批准发布门槛及负责人明确授权 → 执行并回读 Tag/Release 与产物 → 记录已知限制及反馈。构建与安装可重复性要求、产物校验方式、具体脚本和迁移协议待 PH-07/11；不承诺 bit-for-bit 可重现构建或当前 Release 工具已测试。关联 021,025,036,038,040,041,049,052。

S29 五指标作为后续真实部署的参考：变更从提交至部署的耗时、部署频率、失败部署恢复耗时、需干预部署占比、因生产事故导致的非计划部署占比。不能将本项目当前文档提交数当作部署频率，也不能把对话耗时当生产恢复时间；无部署或无数据时标不可测/不适用，不造零值。跨项目/不同复杂度直接比较会产生偏差；WP-06 另研究针对 SRF 用户简单性、真实性、恢复、迭代和经济性的配对任务评价。小批量逻辑变更可作为低风险实验方向，但不拆开原本需要一致提交的文件以追求数量。
