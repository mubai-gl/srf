## 1. 项目背景

通用 AI 对话能够参与需求、设计与编码，但在长期研发中，可能丢失上下文、误解需求、重复建设、越权修改、产生不一致的文档或代码，甚至把未经运行的实现误判为已完成。仅依靠一个长提示词或单一对话，难以使过程稳定、可恢复和可审查。

本项目拟以软件工程专业知识为基础，建立由 AI 运行、由人类控制、由版本化仓库保存成果的通用软件研发协作框架。首期采用 GPT Project 和 GitHub，结合实际可用的工具执行；不是为了重新实现 IDE、编译器或其他工具。用户已在另一项目 SGF 中验证过 GitHub 文件读写能力；SRF 项目的具体权限、操作接口、分支及执行能力仍须独立验证。

## 2. 愿景与使命

**框架内部可以复杂，但用户使用起来必须简单。**

自身迭代性是与用户简单性并列的顶层质量目标：框架可以持续变化，但变更必须可定位、可控制、可验证、可恢复。此目标贯穿所有模块，不只由演进体系负责。

让用户用自然语言表达目标、想法、反馈和决定，由 AI 承担理解、专业分析、研发组织、授权执行、证据检查与记录等复杂工作。关键决策由人类掌握，研发过程可追溯、可恢复、可验证，框架可独立演进。

长期目标：一次研发 SRF，多个软件项目按版本部署；通过软件研发实践反哺框架改进。减少重复建立协作规则的成本，降低对专门编码工具的非必要依赖，但不承诺任何特定产品额度、价格或执行能力。

## 3. 服务对象与角色

- 项目负责人：用户。决定框架方向、重大设计、授权边界、验收及发布；不必填写固定表单、记忆命令或逐项批准低风险细节。
- SRF 研发协作者：SRF 专用 GPT Project 中的 AI。负责框架研究、设计、实现、测试方案、证据整理、维护建议和已授权的仓库操作。
- 软件项目使用者：部署 SRF 的项目负责人及其 AI 协作者。具体软件研发不在 SRF 主项目内开展。
- 外部验证者：CI、编译与测试环境、人工审查者等，提供各自实际能够产生的验证证据。一个 AI 扮演多个角色不等于独立审查。

## 4. 建设范围与非目标

| V1.0 范围 | 非目标或延后范围 |
|---|---|
| 通用规范、最小可运行内核、编排与专业研发能力 | 独立大语言模型、完整 IDE 或编译器 |
| 自然语言交互、协作模式、分级授权、项目配置 | 要求用户学习专有命令或强制一套开发流程 |
| 项目事实、证据、任务上下文、状态恢复 | 收录所有软件工程书籍或维护所有 API 的静态副本 |
| GPT Project/GitHub 适配、工具降级与安全操作 | 承诺所有环境都具备读写、运行或自动化能力 |
| 规则、契约、模板、基础知识、框架测试 | 首版实现全部技术栈或领域扩展、多 Agent 平台 |
| 版本化发布、部署、升级、迁移、回滚与反馈 | 无需授权的自我修改、自动强制全部项目升级 |

首个实际软件实践项目拟为视频剪辑软件。其产品需求、UI、技术栈和业务代码不在本项目预设。其他软件类型通过模拟或小型验证场景检验通用性。SRF 可吸收 SGF 的协作理念，但不依赖 SGF 的文件或内部实现。

## 5. 项目组织与交付形态

1. 建立 SRF 专用 GPT Project 和独立 GitHub 主仓库，由其负责框架自身的需求、研究、设计、规则、测试与版本维护。
2. 框架规范与运行环境分离，V1.0 由 GPT Project 解释和执行规范；重要约束尽可能通过实际工具权限与 CI 实现，首次发布后按需引入分支保护。SRF 自身首次正式发布前只用 main；详细策略见顶层设计 9.2。
3. 正式发布版本化 Release 运行包，包含必要规则、索引、能力规范、模板、适配、运行启动指令及安装升级说明；不将框架研发历史作为运行必需文件。
4. 每个软件独立建立 GPT Project 与 GitHub 仓库，将锁定版本的运行包部署到 `.srf/`，软件自身配置和反馈置于 `.srf-project/`。软件业务文件与 SRF 核心隔离。
5. 软件项目反馈回 SRF 主仓库，在授权、影响分析和回归验证后发布新版本；项目按需升级。

## 6. 成功标准

具体测试指标和阈值在 SRF Project 内设计并确认；下列为立项级验收目标，不是已经通过的结果。

| 维度 | 成功的可观察表现 |
|---|---|
| 易用性 | 普通自然语言能发起、推进、恢复研发，无需学习专有命令 |
| 意图与授权 | 正确区分讨论、决策、实施；在规定边界内执行 |
| 可靠性 | 能识别中断、冲突、缺少权限及证据不足；不伪造完成 |
| 工程质量 | 重要需求、决策、实现及验证可关联；适当选择流程 |
| 通用性 | 在不同软件类别的验证场景中不依赖剪辑软件假设 |
| 经济性 | 与未部署 SRF 的同条件对照相比，能够证明其实际收益并识别额外开销 |
| 可演进性 | 能局部新增、删除、合并或替换模块；定位依赖及规则来源；以回归证据验证改进；能部署指定版本、保护项目配置并验证迁移与回滚；框架迭代不应增加不必要的用户配置负担 |

专业主动性：重要设计由 AI 主动识别遗漏、风险、替代方案和失效假设，不要求用户承担专业完整性审查。结构经济性：保持最小充分文件集合，优先复用与原位更新，不以文件数衡量成果；依据仓库目录规划受控清理冗余。可重建及可退出纳入首版验证目标，具体场景按正式需求确认。

正式发布前必须有可审查的框架测试证据和负责人发布授权。发布后剪辑软件的真实实践是持续改进的来源，不能倒推发布前所有行为已得到保证。

## 7. 约束、假设与主要风险

- GPT Project 是概率性 AI 运行环境，不是确定性工作流引擎；文字规则不能保证每次严格执行。关键约束需要外部保障、实际证据或人工复核。
- GitHub 读写能力因具体环境、授权、工具、分支而异；不以 SGF 的读写成功代替 SRF 实测。不能验证时标明阻塞或降级方案。
- 上下文有限；不要求每次读取所有文件。采用权威事实来源和按需加载，不依赖跨会话记忆。
- 保持精简：避免文档重复、流程膨胀和知识库过度建设。理论引用需核实，不假装读过未取得的资料。
- 软件项目不得未经授权修改框架核心或把敏感业务信息上传至框架反馈渠道。
- 研发中心启动指令不是未来软件 Project 的运行指令，两者不可互换。

普通文件使用稳定名称和路径，原位修改；历史由 Git 管理，不重复维护文件版本号、修订历史或历史副本。整体 Release 与必要的兼容协议版本仍需独立标识；重要设计理由与决策记录不是 Git 历史的重复。

## 8. 启动基线及当前状态

本启动包用于开启 SRF 正式研发，不是可部署的 SRF 运行版本。前期定位、用户简单性、独立仓库与 Project、版本化部署、需求意图管理、框架架构与演进方向已形成共识。详细机制、阈值、目录最终形式、理论版本与实现方案仍待 SRF Project 研究确认。

配套文件：

- `docs/architecture/SRF_TOP_LEVEL_DESIGN.md`：顶层架构与机制。
- `docs/project/SRF_INITIAL_REQUIREMENTS.md`：框架自身的初始需求、边界与验收方向。
- `docs/project/SRF_DEVELOPMENT_ROADMAP.md`：阶段路线、启动流程与移交要求。
- `instructions/SRF_PROJECT_INSTRUCTIONS.md`：SRF 研发中心启动指令（不是正式运行指令）。

- `docs/architecture/SRF_REPOSITORY_LAYOUT.md`：仓库目录规划、文件职责与发布边界。

当前尚未创建仓库或 Project，尚未进行框架实现、理论原典研究或测试。先将启动资料导入 SRF 专用 Project 并配置指令，再在 main 上经授权进行 GitHub 临时文件测试；通过基础测试后才按原路径写入正式基线、核对并建立唯一研发状态。新对话恢复验证通过后再开展框架自身需求规格工作。
