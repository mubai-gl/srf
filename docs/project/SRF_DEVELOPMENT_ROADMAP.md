# SRF 自身研发路线图与启动指南

| 项目 | 内容 |
|---|---|
| 文档编号 | SRF-INIT-04 |
| 目标 | 建立可验证、可发布、可复用的 SRF V1.0.0 |
| 当前阶段 | 顶层设计讨论结束，准备正式研发初始化 |

## 1. 推进策略

先完成框架自身的需求与研究，再进行概要/详细设计、最小内核实现、能力补充、测试和发布。允许受控并行和原型实验：阶段是成果依赖关系，不是无条件的严格瀑布流程。各阶段通过可观察成果进入下一阶段，不预设日程、工作量或费用，也不无限追加顶层概念。

SRF 研发中心初期依据启动指令及研发基线协作；当最小内核可用后，逐步自用（Dogfooding）。先在安全、范围明确的任务上验证，不把未发布规则自动提升为已生效的框架核心。框架理论研究属于新 Project 的工作，不是当前启动包已完成事项。

### 2.1 自身迭代性专项验收（贯穿研发阶段）

- 概要/详细设计阶段：验证模块职责、依赖方向、唯一规则来源、稳定 ID 和契约，明确哪些机制可替换，哪些治理变更须特别授权。
- 文件与协议阶段：普通文件采用稳定路径、原位更新，不附加文件版本号或历史副本；复用 Git 管理历史。框架整体 Release 和确有兼容要求的协议标识保留。
- 最小内核阶段：以受控的真实框架任务试行渐进式自用，模拟新增、删除、合并、替换模块与规则冲突诊断；不要求先实现全部模块。
- 测试阶段：新增框架迭代对照场景，检查正常行为和安全边界是否退化，记录基线、模型/工具环境及失败结果。
- 发布前：验证启动入口兼容、项目配置保护、升级/迁移、失败回滚；具体度量和验收阈值由 SRF Project 设计确认。首版必须能够受控迭代，不把迭代保障整体延后至 V2.0。

- 全阶段主动审视：重要设计与阶段推进前检查遗漏、假设、风险、替代方案、维护成本及失败场景；按风险裁剪。对新增文件优先复用或原位更新，结构性拆分须有职责依据，验收关注重复与加载成本而非机械文件数量。
- 对结构、依赖、引用、配置及发布清单等可确定性验证事项优先使用实际工具；对高不确定性机制使用符合单主分支策略的隔离实验与行为对照，保留失败结论。发布前验证从仓库重建研发环境及已有工程接管、退出场景，记录实际限制。

## 3. 软件工程知识研究工作包（PH-04）

候选起点如下，均未在当前对话进行原典研究、版本核实或正式采用决策。

| 方向 | 候选来源 | 研究问题 |
|---|---|---|
| 软件工程整体 | SWEBOK、IEEE/ISO/IEC 相关标准 | 通用能力覆盖、标准与实践的关系 |
| 项目与业务分析 | PMBOK、BABOK、Scrum、Kanban | 项目治理、需求协商、流程裁剪、重叠与冲突 |
| 软件设计 | SOLID、GoF、DDD、Clean Architecture | 适用条件、替代方案、过度设计风险 |
| 质量和安全 | ISTQB、OWASP、TDD | 验证策略、安全边界、质量门槛 |
| 现代工程 | DevOps、CI/CD、可观测性 | 执行证据、部署、运行与反馈 |
| AI 软件研发 | 上下文工程、AI 编码、Agent 协作实践 | 概率性运行、权限、错误、恢复、评估与成本 |
| 动态技术信息 | 官方文档、成熟开源项目、技术研究 | 时效、API 与版本核验、许可和实践适用性 |

研究步骤：确定所需知识范围 → 获取并核实可用来源与版本 → 研究适用性及证据 → 识别重复、冲突和局限 → 裁剪与融合 → 形成 SRF 自身知识索引、可执行规则或推荐实践 → 通过场景检验。不得把来源名单直接当作规则，不把未读资料描述为已读，不要求复制整本书。若资料无法获得，应记录限制并寻找合法、可靠的替代依据。

优先以框架真实需要的问题组织研究，避免按候选书目机械地逐本研究、形成庞大知识库。研究成果须回到 SRF 自身的设计与测试，不开展剪辑软件业务技术选型。

## 4. 测试与评价安排

### 4.1 框架测试方向

| 场景 | 最低检验重点 |
|---|---|
| 自然语言意图 | 同一需求不同表达、探讨与实施、软件与框架对象区分 |
| 权限和规则 | 越权、已授权细节、核心规则冲突、外部内容诱导 |
| 自适应流程 | 简单修改、复杂模块、低复杂度高风险操作 |
| 状态和恢复 | 新对话恢复、过期状态、部分写入、版本冲突 |
| 证据真实性 | 没有编译工具、测试失败、未执行的测试、状态不一致 |
| 工具降级 | 只读、写入失败、无法构建或运行、外部工具不可用 |
| 版本和迁移 | 安装、兼容检查、项目配置保护、升级和回滚 |
| 通用性 | 桌面/Web/其他类别的最小场景，不预设特定技术栈 |
| 经济性 | 用户交互次数、额外文档量、上下文和工具成本、返工 |
| 回归 | 历史缺陷修复后不再复现；重大行为场景重复运行 |

### 4.2 对照实验

普通 GPT Project 与部署 SRF 的 GPT Project 使用相同任务、尽可能相同模型/权限/工具/初始仓库和验收条件。记录任务完成率、正确性、越权行为、证据真实性、人工参与次数、上下文恢复、时间和可测成本、返工与文档负担。保留失败结果，说明环境差异。正式阈值、样本及重复次数在需求和测试设计阶段确认；不以单次测试证明永久可靠，不假设 SRF 必然优于对照组。

### 4.3 首版发布要求

有实际可安装的版本化产物和独立软件运行指令；核心及关键安全/恢复/真实性/迁移场景达到已确认标准；记录已知局限及尚未具备能力；完成发布前检查及负责人授权。首版发布后安排剪辑软件真实实践；若存在阻塞缺陷，不能因已写完文档而自动发布。

## 5. 现在如何启动 SRF 专用 GPT Project

以下为人工安装步骤，不代表已经代用户完成。

1. 在 GitHub 创建独立仓库（建议名 `SRF`，私有或公开由用户选择），初始化 README 并确认默认分支为 `main`。在 ChatGPT 创建专用 Project `SRF · 研发中心`，确认该 Project 可访问目标仓库，仅授予必要权限。
2. 解压启动包，上传九份 Markdown 至 Project（至少五份章程、需求、路线图、顶层设计、目录规划；另四份为 README、AGENTS、当前状态及指令文件，供完整初始化使用）。打开 `instructions/SRF_PROJECT_INSTRUCTIONS.md`，将标记之间的正文复制至项目指令设置。`.gitignore` 也必须按原内容提供给初始化过程（若不能上传该文件或 ZIP 无法读取，直接提供文本或通过本地 Git 导入）。不依赖 AI 猜测未读文件内容。Project 上传可平铺文件，GitHub 按原目录写入。
3. 在新 Project 提供实际 GitHub 仓库地址或 `owner/repo`，发送下方启动语句。核对启动资料、仓库、`main`、权限和可用工具。经授权后，先执行下方临时文件测试。此时尚不写入正式启动基线。
4. 基础操作验证通过后，按明确初始化授权将十个真实文件写入 GitHub 原路径；已有 README 等先读取和比较，保护无关内容。不能精确读取或写入时说明限制，不自行重建缺失文件；必要时使用经授权的本地 Git 导入并核实。依赖多文件优先同一逻辑提交，否则在 `main` 串行写入并核对完整性；不创建其他分支。建立唯一状态记录，保存实际验证证据及后续未验证项，不创建重复日志或空目录。
5. 核对远端文件清单、内容、提交及入口引用，确认临时文件已清理。新建一个 SRF Project 对话，仅发送“继续 SRF 的研发工作”，验证能否从仓库恢复当前阶段、有效规则、任务与下一步；失败则修复入口/配置并重测，不依赖旧对话。
6. 初始化及恢复验证通过后，再启动 PH-03。仓库成为持久化事实来源；上传快照仅供启动或故障恢复，不能覆盖 GitHub 中的有效当前版本。

### 初始化能力验证（PH-02）

测试在 SRF 专用 Project 内、导入启动资料与指令之后、正式基线写入 GitHub 之前执行。首次发布前只使用 `main`，不创建测试分支或 PR。经明确任务授权后：

| 测试项 | 当前要求及证据 |
|---|---|
| 仓库身份/目录/读取 | 核实 owner/repo、默认分支 main、当前提交和 README 内容；核实权限与实际工具 |
| 新增/读回/中文 UTF-8 | 在经核对不存在的唯一临时路径写入含中文的无敏感内容文本，读回逐项比对并记录 blob SHA 与 commit |
| 更新/冲突保护 | 读取完整内容及最新 blob SHA，原位更新并核对差异；在临时文件范围内验证陈旧 SHA 不会覆盖当前内容（可用且安全时） |
| 移动/删除/历史恢复 | 按操作协议仅移动或删除临时文件，检查新旧路径；读取历史提交中的临时内容并恢复后再清理 |
| 批量提交 | 工具支持时，以最少临时文件测试同一逻辑 commit 增改删、保留其他路径及核对差异；不可用则记录串行降级，不冒称原子提交 |
| 超时/部分失败 | 核实远端状态再重试，使用实际安全测试或明确标为模拟/未测，不人为破坏正式文件 |
| 分支/PR/分支合并 | 首次正式发布后且启用前验证；当前明确延后，不算通过 |
| Tag/Release | 首次发布时实际核实，不提前创建正式版本 |

基础门槛为实际读取、创建、更新、删除、中文内容核对及结果验证成功；批量能力等未通过时记录限制和安全降级方式。基础能力不足则暂停自动初始化，向用户报告并取得采用本地 Git 等替代方案的授权。所有写入严格限定临时路径，不覆盖正式文件。验证结束核对最终目录与基线相比没有无关改变，临时文件从工作树删除但测试提交留在 Git 历史。证据包括实际 commit SHA、路径、结果及限制，初始化时写入现有 `management/PROJECT_STATE.md` 或必要 Issue 引用，不新建常规测试日志。

### 首次启动语句（复制到 SRF Project 对话）

> 现在正式启动 SRF 自身的研发。请读取本 Project 中的研发启动包，核对章程、顶层设计、初始需求、路线图和仓库目录规划。我的目标是独立研发 SRF V1.0.0，不是现在开发剪辑软件。目标仓库由我提供，首次正式发布前仅使用 main，不建其他分支、不使用 PR。请先检查实际仓库与工具权限；在得到我的测试授权后，在 main 上以临时文件实测基础读增改删、中文编码、差异核对及可用批量能力，清理测试文件并报告证据。基础通过后，在获得初始化写入授权时按原路径持久化十个启动文件，核对远端内容及唯一状态。随后由我新开对话验证现场恢复，通过后再开展正式需求规格。软件工程理论研究放在本 Project 后续阶段进行，不要将候选知识直接当成已确认规则。未实际完成的操作请明确标注。

仓库标识和分支由使用者补充，不应由 AI 猜测。若无法使用 GitHub 写入工具，保留可应用的文件内容或补丁，由用户或已授权执行环境应用并核实。

## 6. 交接与后续研发纪律

每次恢复任务时，以已确认的仓库身份、当前状态、任务授权及相关基线为依据；只读必要内容。每次有重要变更时，记录决策、实际差异、证据和待办。已知事实不重复询问；影响顶层方向、首版范围、治理规则和发布的决策必须由负责人明确确认。

V1.0 发布后，另建软件 Project 和软件仓库，部署正式运行包并使用软件 Project 的运行指令。当前研发启动包只用于研发 SRF，不可冒充正式发布产物。
